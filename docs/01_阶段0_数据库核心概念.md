## 对应代码位置

本阶段不写代码，但可以提前**对照看**代码骨架里「类 ↔ 表」的映射关系，先混个眼熟：

| 概念 | 对应代码文件 |
| --- | --- |
| 表 | `powerdb/models/*.py` 里每个 `__tablename__ = "..."` 就是一张表 |
| 行（一条记录） | 每个类的一个实例 = 一行数据 |
| 列 / 字段 | 类里的 `id`、`name`、`value` 等属性 |
| 主键 | `id: Mapped[int] = mapped_column(primary_key=True)` |
| 外键 | `mapped_column(ForeignKey("samples.id"))` |
| 一对多关系 | `relationship(back_populates="...")` |

> 例：`Sample`（样品）里的 `project_id = ForeignKey("projects.id")` 表示「一个样品属于一个项目」，
> 而 `Project.samples` 的 `relationship` 表示「一个项目有多个样品」——这是一对多。

## 基础知识详解

### 1. 表、行、列
把「表」想象成一个 **Excel 工作表**：
- 行 = 一条记录（一个样品、一次试验、一个测量值）。
- 列 = 这条记录的一个属性（名称、型号、值、单位）。
- 与 Excel 不同，数据库强制每一列有明确类型，且行是无序的（不能靠"第几行"定位，靠主键定位）。

### 2. 主键（Primary Key）
每张表至少有一个主键，用于**唯一标识一行**。就像身份证号，全局唯一、不可为 NULL。
骨架里每张表都用自增整数 `id` 做主键，简单可靠。

### 3. 外键（Foreign Key）与关系
外键是「指向另一张表主键」的列，用来表达表之间的**关系**：
- 一对多：一个 `Project` 有多个 `Sample`（`Sample.project_id → projects.id`）。
- 一对一 / 多对多：本业务暂用不到多对多，先掌握一对多即可。

关系基数决定「外键写在哪一边」：**「多」的那一边持有外键**。
例：一个样品有多次试验，所以外键 `sample_id` 写在 `test_runs`（多的一方）。

### 4. 范式（Normalization）
范式是「怎么拆表、怎么避免冗余」的规则，初学只需理解前三个（1NF~3NF）：
- **1NF**：每列只存放一个原子值（不要在一个单元格里塞 "1,2,3"）。
- **2NF**：非主键列完全依赖主键（消除部分依赖）。
- **3NF**：非主键列不依赖其他非主键列（消除传递依赖）。

**为什么重要**：如果在一个 `samples` 表里重复写「项目名称」，项目改名时就得改无数行，容易不一致；
拆出 `projects` 表用外键引用，改名只改一行。

### 5. ER 图
实体（方框）+ 关系（连线，标注基数 1 / N）。画 ER 图是数据库设计的第一步，也是和同事对齐的通用语言。
