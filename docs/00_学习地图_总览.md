## 0. 一页总览（先看结论）

| 维度 | 结论 |
| --- | --- |
| 起点技术栈 | 已有 Python + Pytest + 仪器控制 + 时序分析 + Excel/Json 归档 |
| 数据库选型 | **SQLite（本地起步）→ PostgreSQL + TimescaleDB（集中进阶）** |
| 统一访问层 | **SQLAlchemy 2.0**（ORM + Core），换库只改一行连接串 |
| 迁移管理 | **Alembic**（schema 版本化） |
| 边界校验 | **Pydantic**（入参/出参契约） |
| 高频波形 | **元数据入库 + 原始波形落文件**（Parquet/NPY/HDF5）混合存储 |
| 分层结构 | `models` → `repositories` → `services` → `schemas`（依赖单向） |
| 最终能力 | 横向对比 / 看板只读接口 / AI 分析接口，同源于 Service 层；Excel 导出面向业务交付 |

**三个关键原则**：

1. **代码与逻辑分离**：数据库访问只存在于 `repositories`；业务逻辑只在 `services`；调用方永远不直接写 SQL。
2. **单一数据访问出口**：所有读写都走 `session_scope` 事务上下文。
3. **渐进不重写**：新增「数据库归档」目标，与文件归档并行，逐步切换。

## 3. 技术选型与理由

| 组件 | 用途 | 为什么选它 |
| --- | --- | --- |
| SQLite | 入门 + 本地单机 | 零配置、单文件、标准库自带 |
| PostgreSQL | 目标生产库 | 强一致、JSONB、并发、多用户读 |
| TimescaleDB | 时序扩展 | hypertable 自动分区，时序聚合快 |
| SQLAlchemy 2.0 | ORM/Core 统一层 | **换库只改连接串**，屏蔽方言差异 |
| Alembic | 迁移 | schema 版本化 |
| Pydantic | 边界模型 | 参数校验、出参序列化契约 |
| DuckDB（可选） | 列式分析 | 高频波形/大结果集极速聚合 |
| Parquet/NPY/HDF5 | 高频原始波形 | 数据库不适合存海量高频点 |

> **最关键判断**：SQLAlchemy 让你「先在本地 SQLite 学会全部概念并跑通业务」，
> 需要集中部署时把连接串从 `sqlite:///...` 换成 `postgresql+psycopg://...`，业务代码几乎不动。

## 4. 总体分层架构

依赖方向**严格单向**，上层只调用紧邻下层：

```
┌──────────────────────────────────────────────────────────────┐
│  调用层：Pytest 用例 · 仪器控制脚本 · 归档脚本 · 看板API · AI  │
└─────────────────────────────┬────────────────────────────────┘
                              │ 只调用 Service
┌─────────────────────────────▼────────────────────────────────┐
│  services 服务层（业务逻辑）                                   │
│  comparison_service · timeseries_service                     │
└─────────────────────────────┬────────────────────────────────┘
                              │ 只调用 Repository
┌─────────────────────────────▼────────────────────────────────┐
│  repositories 仓储层（唯一接触 ORM/SQL 处）                    │
│  Repository(基类) · MeasurementRepository · TimeSeriesRepo..  │
└─────────────────────────────┬────────────────────────────────┘
                              │ 只操作 models
┌─────────────────────────────▼────────────────────────────────┐
│  models 模型层（表结构映射，9 张表）                            │
└─────────────────────────────┬────────────────────────────────┘
                              │ 经由 core
┌─────────────────────────────▼────────────────────────────────┐
│  core（engine/session/base/config）── SQLite → PG+TimescaleDB │
└──────────────────────────────────────────────────────────────┘
   schemas（Pydantic）横向贯穿边界：入参校验 + 出参序列化
```

各层职责：

| 层 | 只做 | 绝不做 |
| --- | --- | --- |
| core | 建引擎、会话、事务、建表、配置 | 不写业务 |
| models | 定义表/字段/关系 | 不做查询逻辑 |
| repositories | 增删改查、复杂 SQL | 不做业务判断 |
| services | 业务流程编排、统计、对比、降采样 | 不直接写 SQL |
| schemas | 进出边界校验与序列化 | 不碰数据库 |

## 5. 数据模型设计（贴合电力电子测试业务）

```
Project(项目/产品)
  └─ Sample(被测样品/设备)
        └─ TestRun(一次试验批次)
              └─ TestRecord(针对某标准测试项的一条记录)
                    ├─ Measurement(标量结果：效率/温升/谐波…)
                    └─ TimeSeriesChannel(时序通道:Ua/Ia/P…)
                          └─ TimeSeriesPoint(采样点 t/value)

Standard(能标/国标)
  └─ StandardItem(测试项，含限值)

Instrument(仪器仪表，连接信息走 JSON)
```

**时序混合三层存储**（重点）：元数据入库 → 高频原始波形落文件（`raw_path` 索引）→ 降采样点入长表。

## 7. 与现有 Pytest 架构的集成

```python
# 方式一：fixture 管理生命周期（推荐）
@pytest.fixture(scope="session", autouse=True)
def database(tmp_path_factory):
    init_engine(DatabaseConfig(url=f"sqlite:///{tmp_path_factory.mktemp('db')}/test.db"))
    create_schema(drop=True)
    yield

# 方式二：在测试用例内显式写结果
def test_efficiency(...):
    result = measure_eff(...)
    with session_scope() as s:
        s.add(Measurement(test_record_id=..., metric="efficiency", value=result, unit="%"))
```

**渐进替换 Excel/Json**：归档模块保留，新增 `DbArchiver`（内部调 Service），文件归档与数据库归档并行，稳定后写一次性 `import_legacy.py` 把历史文件导入数据库。

## 8. SQLite → PostgreSQL 迁移路线（先本地后集中）

1. 本地阶段：`POWERDB_URL` 默认 `sqlite:///powerdb.db`，`create_schema` 快速起步。
2. 引入 Alembic 后，用迁移替代 `create_schema` 管结构。
3. 部署 PG：改 `POWERDB_URL=postgresql+psycopg://user:pass@host:5432/powerdb`，业务零改动。
4. 时序进阶：`timeseries_points` 建 TimescaleDB hypertable（按 `t` 分区）。
5. 高频波形：原始数据继续落文件，主库存索引，DuckDB 旁挂分析。
6. 注意点：JSON 在 SQLite 是 TEXT、PG 是 JSONB（骨架用 `with_variant` 自适应）；并发写用连接池。

## 11. 常见坑与 FAQ

- **Q：为什么不一开始就上 PostgreSQL？** 先本地 SQLite 零运维快速迭代，SQLAlchemy 保证后期切换零成本。
- **Q：高频波形要不要进数据库？** 不要逐点进关系表，元数据 + 文件 + 路径索引是通用做法。
- **Q：循环 add 写时序为什么慢？** 每条 ORM 都触发 flush，批量 `insert(...).executemany` 快一个量级。
- **Q：怎么保证不出脏数据？** 所有写走 `session_scope` 事务，异常回滚；入参 Pydantic 校验。
- **Q：换库真的不用改代码吗？** 只要不写死方言、不直接用 dbapi，只改 `POWERDB_URL` 即可。
