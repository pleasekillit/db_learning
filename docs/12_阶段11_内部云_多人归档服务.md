# 阶段 11 · 内部云：多人归档服务

> 团队 3 人、长期 ≤10 人，一台内网 Windows PC 当归档服务器。把前面所有分层能力包成一个
> REST 服务，让大家**共用同一个库、能提交、能归档、能维护**，而不是各管各的 Excel。
>
> 代码入口：[api/app.py](../../powerdb/powerdb/api/app.py)、[maintenance.py](../../powerdb/powerdb/maintenance.py)、
> 演示脚本：[internal_cloud_demo.py](../../powerdb/examples/internal_cloud_demo.py)

## 架构决策（先想清楚再动手）

| 决策点 | 起步方案 | 成长方案（人多 / 数据大时） |
| --- | --- | --- |
| 数据库 | SQLite（单文件，零运维） | PostgreSQL（多写并发、更强） |
| 访问方式 | 一个 FastAPI 网关进程独占写 + HTTP 供多用户 | 同左，DB 换 PG、连接串改一行 |
| 文件归档 | 内网共享目录（SMB/本地盘），路径入库 | 同左，可上 NAS / 对象存储 |
| 为什么"单网关 + SQLite"够用 | ≤10 人写并发很弱，单进程写串行化，规避 SQLite 多写者问题 | 人多了才值得上 PG 服务 |

> **关键点**：换库只改环境变量 `POWERDB_URL`，业务代码一行不动——这正是前面
> `config.py` + SQLAlchemy 分层带来的收益（阶段 5 埋的伏笔在这里兑现）。

## 四大能力 → 接口映射

| 能力 | 接口 | 说明 |
| --- | --- | --- |
| **管理** | `POST/GET /api/projects`、`/api/samples`、`/api/standards`、`/api/standard-items` | 建项目/样品/标准/测试项 |
| **提交** | `POST /api/runs` | 一次提交完整试验 + 记录 + 测量值（仅内网 IP） |
| **归档** | `POST /api/records/{id}/files`、`GET /api/records/{id}/files/{name}`、`GET /api/archive` | 上传原始文件、下载取回、列出归档 |
| **查询/导出** | `GET /api/comparison`、`/api/judge`、`/api/export/case-records`、`/api/export/judge` | 复用前一章判定与导出 |
| **维护** | `GET /api/maintenance/health|stats`、`POST /api/maintenance/backup` | 健康/统计/备份 |

> 访问控制：`/api/runs` 挂 `require_intranet` 依赖（[api/deps.py](../../powerdb/powerdb/api/deps.py)），
> 只放行内网私有网段 `10/8`、`172.16/12`、`192.168/16`、本机 `127/8`，公网直连返回 `403`。
> 白名单可用环境变量 `POWERDB_ALLOWED_CIDRS` 覆盖（逗号分隔）。这是最基础的防线，更强在前置 nginx 做 IP 白名单或加登录鉴权。

## 部署（内网 Windows PC）

1. 装依赖：`pip install -r requirements.txt`
2. 启动服务：
   ```bash
   uvicorn powerdb.api.app:app --host 0.0.0.0 --port 8000
   ```
3. 同事浏览器打开 `http://<这台PC的内网IP>:8000/docs`，就能看到带"试用"按钮的接口文档，点一下即可提交。
4. 长期跑：用 `nssm` 或"任务计划程序"把 uvicorn 设成开机自启的 Windows 服务。
5. 备份自动挂：`POST /api/maintenance/backup`（或直接定时跑），把 `.bak` 存到另一块盘/另一台机。

## 归档目录设计（文件与数据库不脱节）

```
archive/                      # 内部云文件区（= POWERDB_ARCHIVE_DIR）
  └── R-2026-001/             # 按试验编号分目录
        └── EFF_满载.parquet  # 原始文件
```

`data_files` 表登记：`name`（给业务看，导出到 Excel） + `path`（给程序回查） + `kind`（raw/report/log/image）。
这样"数据库里的记录"和"硬盘上的文件"一一对应，团队任何一个人都能顺着记录找到文件。

## 维护三件事

- **健康检查**：库是否连通、存档盘占了多少、有多少文件（`GET /api/maintenance/health`）。
- **统计**：每张表多少行，一眼看清资产规模（`GET /api/maintenance/stats`）。
- **备份**：SQLite 走 `sqlite3` 自带 backup API（WAL 下也一致安全）；换 PostgreSQL 后用 `pg_dump` 挂计划任务。

## 运维备忘（容量 + 备份周期，写死成制度）

> 内网 PC 要长期当归档服务器，"不做容量规划、不定备份周期"是最常见的翻车点。
> 下面给一套可直接套用的起点数字，实测 1~2 个月后按真实数据修正。

**容量估算（单台 ≤10 人电力电子测试团队）**

| 数据 | 单次量级 | 一年量级（粗） | 说明 |
| --- | --- | --- | --- |
| SQLite 库文件 | KB~MB | 几百 MB~几 GB | 只存"元数据 + 测量值"，不大 |
| 归档原始波形 | 一次试验 10MB~数百 MB | **这才是大头** | Parquet/NPY/HDF5 落文件区 |

- 经验分配：**给归档文件区预留 ≥ 数据库体积的 10~20 倍**。
- 做法：先挑一个典型项目，跑 1 个月，看 `GET /api/maintenance/health` 里的 `archive_bytes` 增长速度，
  反推 `年需求 = 月增量 × 12`，再按 `需求 × 2` 留盘（预留增长与临时空间）。

**备份周期（3-2-1 简化版，够小团队用）**

| 频率 | 动作 | 保留 |
| --- | --- | --- |
| 每日 | SQLite 全量 `.bak`（backup API）+ 归档目录 robocopy 到第二块盘/NAS | 最近 7 份日备 |
| 每周 | 同上，另存一份到另一台机 | 最近 4 份周备 |
| 每月 | 归档盘整体快照 | 最近 12 份月备 |

- 关键原则：**备份至少落在另一块物理盘/另一台机**，别和主库同一块盘。
- 自动挂法：Windows「任务计划程序」建两条任务——① 每日 02:00 跑 `POST /api/maintenance/backup`；
  ② 每日 03:00 跑 `robocopy <归档目录> \\NAS\backup /MIR`。

## 训练 Demo 详解

**运行**（项目根目录 `/workspace/powerdb` 下，脚本会自动用临时库、临时归档目录）：
```bash
python examples/internal_cloud_demo.py
```
走通并打印：管理建库 → 提交一次试验 → 上传归档文件 → 判定/导出 → 健康/统计/备份，
最后给出生产环境的 `uvicorn` 与 `curl` 命令。

**进阶练习**：
- `uvicorn powerdb.api.app:app --reload` 真启一次，浏览器打开 `/docs` 点击试用各接口（含上传/下载）；
- 把 `require_intranet` 同样挂到其余写接口（`/api/projects`、`/api/samples` 等），收紧整站访问；
- 用 `nssm install PowerDB uvicorn ...` 把服务注册成 Windows 服务，重启机器验证自启；
- 按「运维备忘」建好任务计划程序的每日备份 + robocopy，跑一周确认 `.bak` 与归档副本都在。
