# 阶段 9 · 价值演示与资源争取

> 数据库是"人类看不懂的东西"吗？对，因为它的价值不在"怎么存"，而在"业务问题多快能得到答案"。
> 本章教你**怎么向业务（电力电子硬件工程师）演示数据库的价值**，进而为项目争取更多
> **硬件资源**（台架、器件、样机）和**开发时间**。

## 本章目标
- 说清楚业务为什么会觉得"数据库看不懂"，以及怎么扭转这个认知。
- 掌握"三段式演示法"：先发问 → 跑脚本 → 交付一份他们熟悉的 Excel。
- 用五个价值点（尤其"省硬件"）把数据库从"软件成本"讲成"省钱手段"。
- 会用 `value_demo.py` 做一场有冲击力的现场演示。

## 基础知识详解

### 1. 为什么业务说"数据库看不懂"

沟通用错了语言。开发讲的是「表 / 外键 / 范式 / 第三范式」，业务听到的是天书；
但业务真正的问题是「所有批次的效率趋势、哪几批超限」「这个测试项历史做过几次」。
**同一个系统，用"答案"开场就是工具，用"结构"开场就是负担。**

### 2. 三段式演示法（现场这样演）

1. **先发问**：问一个他平时被折腾过的真实问题，例如"要给我司所有 PCS-100 的额定效率趋势，
   还得标出哪几批低于 95%，你现在怎么查？要多久？"（他通常会答"翻 Excel，半小时起步"）。
2. **跑脚本**：`python examples/value_demo.py`，一条查询毫秒级出结果，自动标超限、算均值。
3. **交 Excel**：脚本最后导出中文表头的 xlsx，落回他熟悉的 Excel——让他亲手打开确认。

> 对比要**可量化**：把"半小时 vs 3 毫秒"当场说成数字，冲击力远大于"很快"。

### 3. 五个价值点（按"对争取资源"的优先级排列）

| 价值 | 一句话给业务 | 怎么量化（讲具体数字） |
| --- | --- | --- |
| **省硬件** | 同型号历史数据可复用做横向对比，新项目少做重复测试 | "重测一轮温升占台架 X 小时 / 耗电 Y 度 / 器件 Z 元" |
| 省时间 | 季度汇总报告从 1~2 人天 → 0 人天 | 用你团队真实的人工工时算 |
| 少出错 | 每笔数据带时间戳/操作员/状态，可追溯 | 举一个"Excel 被人覆盖改坏"的实例 |
| 数据资产 | 项目结束 Excel 散落丢失，DB 让数据成为团队资产 | "人来人走，数据都在" |
| 为 AI 铺路 | 结构化、可切片历史数据是 AI 故障诊断/寿命预测的前提 | 先攒数据，后期才有算法用武之地 |

> **关键判断**：把"数据库"定位成"少做重复测试、少占台架、少烧器件"的省钱手段，
> 而不是"多一套软件"。这是争取硬件资源最有力、也最容易被忽略的一句话。

### 4. 别把演示做成"技术汇报"

- 不讲表/键/范式，只讲"业务问题 → 秒级答案"。
- 不用让他看 SQL、看代码、看命令行报错；给他一个 Excel/图表就够了。
- 提前准备 2~3 个**真实业务问题**，而不是通用示例——问题越贴他的工作，越有说服力。

## 训练 Demo 详解

**准备**（项目根目录 `/workspace/powerdb` 下）：
```bash
python examples/value_demo.py
```
脚本会依次回答三个问题并打印"没数据库时要多久"的对比：
1. 所有批次额定效率趋势 + 均值 + 超限批（一条查询 3ms）；
2. 整体通过率 + 失败最多的测试项；
3. 导出用例执行记录 Excel（`exports/价值演示_用例执行记录.xlsx`）。

**进阶练习**：
- 把脚本里的演示数据 `RUNS` 换成你真实项目的 1~2 个型号数据，重跑就是你的专属演示。
- 给"省硬件"补一个真实数字（台架小时 / 耗电 / 器件成本），写进 `ROI_NOTES` 再演一次。
- 结合 [阶段7 的 Excel 导出](08_阶段7_Excel导出_业务交付.md)，把"导出 Excel"这一环做成收尾动作。
