> 什么时候提交、怎么改表结构不丢数据、怎么把时序写入做得快。

## 基础知识详解

### 1. 事务与 ACID
- **A**tomicity 原子性：一组操作要么全成功要么全失败。
- **C**onsistency 一致性：事务前后数据都符合约束（外键、唯一等）。
- **I**solation 隔离性：并发事务互不干扰。
- **D**urability 持久性：提交后不因崩溃丢失。

骨架里 `session_scope` 就是事务边界：`yield` 内做业务，正常 commit、异常 rollback、最终 close。

### 2. Alembic 迁移
「改表结构」应该用迁移脚本，而不是手动 `ALTER`。典型流程：
```bash
python3 -m alembic init ...        # 只需一次（骨架已配好）
python3 -m alembic revision --autogenerate -m "add column x"   # 生成迁移
python3 -m alembic upgrade head    # 应用
python3 -m alembic downgrade -1    # 回滚一步
```
> 骨架 `env.py` 已统一从 `DatabaseConfig` 读 URL，并给 SQLite 开了 `render_as_batch`（因为 SQLite 不原生支持 `ALTER`）。

### 3. 连接池
- SQLite：基本单写多读，长连接少。
- PostgreSQL：可用连接池复用连接，`pool_size`/`pool_recycle` 在这里才真正有意义（防长连接被中间层断开）。

### 4. 批量写入 vs 循环 add

写时序点切忌逐条 `session.add`——每条都会走一遍对象状态追踪与 flush，上万点下来性能差一个数量级。

```python
# 慢：每条触发对象追踪 + flush，多次往返
for t, v in raw:
    session.add(TimeSeriesPoint(channel_id=cid, t=t, value=v))
session.commit()
```

```python
# 快：一次往返批量 insert（底层走 executemany）
from sqlalchemy import insert

session.execute(
    insert(TimeSeriesPoint),
    [{"channel_id": cid, "t": t, "value": v} for t, v in raw],
)
session.commit()
```

骨架里的 `bulk_insert_points()`（`powerdb/repositories/timeseries_repository.py`）用的就是后者。

### 5. 改表结构 → 快速迁移到其他项目

**核心结论：不要靠「复制 models 代码」来同步表结构，要靠 Alembic 迁移脚本这条可重放的历史链。**

- `models/` 里的 `Mapped` / `mapped_column` / `ForeignKey` 是「**代码层面的表设计**」；
- `powerdb/migrate/versions/` 里的每个 `.py` 是「**数据库层面的、可回放的建表/改表指令**」，才是表结构的**唯一事实来源**；
- 别的项目想得到和你一模一样的表结构，只需拿到 `alembic.ini` + `powerdb/migrate/`（含 `env.py`、`versions/`），跑一句 `alembic upgrade head`，**不必把你的整个 models 业务代码搬过去**。

你的项目已生成基线迁移 `versions/bc6eedfbd0dc_baseline_init_schema.py`（11 张业务表 + 索引 + 外键），这是「迁移到其他项目」的起点。

#### 5.1 修改表结构的标准流程

```bash
cd /workspace/powerdb
export POWERDB_URL="sqlite:///your_db.db"

# 1) 改 models/（例：给 project.py 的 Sample 加一列 temperature_offset）
# 2) 自动对比 models 与数据库差异，生成迁移
python3 -m alembic revision --autogenerate -m "add temperature_offset to samples"
# 3) 人工审查生成的脚本（重点看下面「两个坑」）
# 4) 应用迁移
python3 -m alembic upgrade head
# 5) 回滚一步再升回来，确认可逆
python3 -m alembic downgrade -1
python3 -m alembic upgrade head
```

**审查时注意两个坑**：
- `JSON().with_variant(JSONB(), "postgresql")` 自动生成时可能把 `Text` 渲染成裸名，需补成 `sa.Text()`（本项目基线迁移 `bc6eedfbd0dc` 已修正 3 处）。
- SQLite 不原生支持 `ALTER`，`env.py` 已开 `render_as_batch` 并用 `op.batch_alter_table` 改写表，生成出的 batch 代码是正常现象，别误删。

#### 5.2 迁移到另一个项目的三种方式

| 场景 | 怎么做 |
| --- | --- |
| ① 全新空白库 | 把 `alembic.ini` + `powerdb/migrate/` 复制过去，`alembic upgrade head` 即得同构库 |
| ② 已有数据、要从半路接上 | 老库先 `alembic stamp head` 把当前结构标记为「已到最新」，之后只走增量 `revision --autogenerate` |
| ③ 对方没有 Python 环境 | `alembic upgrade head --sql` 导出离线纯 SQL 文件，直接给对方数据库执行 |

无论哪种方式，**「迁移脚本是唯一事实来源」**：任何「手动在库里 ALTER 过」的操作都会让迁移链与真实库脱节，之后 `autogenerate` 就会产生噪声。

## 训练 Demo 详解

**任务一（事务）**：在 `session_scope` 里制造一次异常（如 `raise ValueError`），验证：
- 异常前 `add` 的数据被回滚；
- 异常被原样抛出，便于上层捕获。

**任务二（迁移）**：
```bash
cd /workspace/powerdb
export POWERDB_URL="sqlite:///migration_demo.db"
python3 -m alembic revision --autogenerate -m "init schema"   # 首次生成完整建表
python3 -m alembic upgrade head
# 再给某表加一列，重复 revision --autogenerate + upgrade
```
验证：加列后旧数据不丢；`downgrade -1` 能把结构退回。

**任务三（性能对比）**：写一段代码，向 `timeseries_points` 写入 1 万点：
- 用「循环 add」计时；
- 用 `bulk_insert_points` 计时；
- 记录两者耗时差异（通常差一个数量级）。

**验证标准**：能解释「为什么时序点要批量写、为什么改结构要走迁移而不是手动改表」。
